# UI Help и Discoverability — план реализации

> Статус: реализовано, документ также фиксирует дальнейшие UX-направления.
>
> Этот документ описывает не только отдельную Help-страницу, но и всю систему
> discoverability: как пользователь понимает текущее состояние интерфейса,
> доступные действия и результат следующего нажатия.
>
> Help-страница является справочником второго уровня. Она не заменяет
> контекстные подсказки внутри Library, Settings и Presets.

## 1. Цель

Пользователь должен без предварительного чтения README понять:

- что сейчас открыто;
- какой объект выбран;
- какая панель и какой элемент имеют фокус;
- что произойдет после `Enter`;
- что сделает `Back` в текущем состоянии;
- как перейти к соседней панели или странице;
- как отменить потенциально опасное или незавершенное действие;
- где найти подробное описание управления и возможностей приложения.

Для нового пользователя интерфейс должен быть объяснимым через наблюдение.
Для опытного пользователя подсказки не должны мешать быстрому управлению.

## 2. Проблема и границы

### 2.1. Что не решает Help-страница

Отдельная Help-страница не решает следующие проблемы:

- пользователь не знает, что `Left/Right` переключают панели;
- пользователь не видит, что Settings находятся в режиме редактирования;
- пользователь не понимает, какой смысл имеет `Back` прямо сейчас;
- пользователь не различает локальный источник и remote-каталог;
- пользователь не видит доступное действие над выбранным объектом;
- пользователь не понимает, почему Enter ничего не сделал или запустил другой сценарий.

Эти состояния должны объясняться непосредственно в основном интерфейсе.

### 2.2. Что входит в этот план

В план входят:

1. постоянная или почти постоянная строка контекстных действий;
2. визуальное отображение состояния фокуса и режима;
3. отдельная Help-страница с тематической навигацией;
4. контекстный вход в Help;
5. единый источник истины для mapping и текстов;
6. тестирование discoverability через состояния и сценарии.

### 2.3. Что не входит в первую версию

Не входят в первую версию:

- интерактивный tutorial;
- полноэкранные onboarding-экраны;
- поиск по Help;
- локализация Help на несколько языков;
- rich text, markdown или HTML-рендеринг;
- mouse hover и tooltip-модель;
- динамическая генерация справки из произвольного runtime-кода.

## 3. UX-модель: четыре уровня объяснения

### Уровень 1 — состояние

Интерфейс всегда показывает:

- страницу: `Library`, `Settings`, `Presets`, `Help`;
- источник: `Music`, `Modland`, `ModArchive`, `Microphone`;
- breadcrumb текущего пути;
- активную панель;
- активную строку или значение;
- особый режим: `Editing`, `Confirm delete`, `Loading`, `Error`.

### Уровень 2 — ближайшее действие

В нижней части overlay показываются действия, применимые к текущему
состоянию. Строка не должна быть общей инструкцией на все случаи.

Примеры:

```text
Enter Open/Play   Back Up   Left/Right Focus   Up/Down Navigate   L1/R1 Pages
```

Для правой панели локального источника:

```text
Enter Activate   Back Library   Up/Down Action   Left/Right Focus
```

Для редактирования Settings:

```text
Enter Apply   Back Cancel   Up/Down Change value
```

Для подтверждения удаления:

```text
Enter Confirm delete   Back Cancel
```

Для Help:

```text
Up/Down Topic   Left/Right Focus   Back Return
```

### Уровень 3 — Help по теме

Help объясняет текущую область подробнее: управление, источники, каталоги,
настройки, пресеты, форматы и устройство.

### Уровень 4 — внешняя документация

README и остальные документы описывают установку, ограничения платформы,
сборку и технические детали, которые не должны перегружать runtime UI.

## 4. Контекстная строка действий

### 4.1. Общее поведение

Добавить отдельный логический блок `ActionHints`, который получает состояние
UI и возвращает список коротких действий для отображения.

Рекомендуемая модель:

```go
type UIHint struct {
    Key   string
    Label string
}

func (o *Overlay) ActionHints() []UIHint
```

Рендеринг подсказок не должен сам анализировать `focusPanel`, `uiPage` или
`ncConfirm`. Это состояние должно быть преобразовано в hints на уровне модели,
а renderer только раскладывает готовые элементы.

### 4.2. Приоритет действий

В строке показывать максимум 3–5 действий. Приоритет:

1. основное действие над выбранным объектом;
2. отмена или безопасный выход;
3. переключение фокуса;
4. навигация по списку;
5. менее частые действия, например смена страницы.

Если доступных действий больше, использовать сокращенные группы, а не
уменьшать шрифт до нечитаемого размера.

### 4.3. Активный способ управления

В основном overlay всегда показывается только один mapping:

- при наличии подключенного джойстика — только названия кнопок джойстика;
- если джойстика нет — только клавиатурные клавиши;
- полный mapping обоих способов управления доступен внутри Help, но не в
   компактном runtime footer;
- при подключении или отключении джойстика активный mapping обновляется без
   перезапуска приложения.

Это основной UX-контракт. Одновременный вывод `Enter` и `A/B` в основном
интерфейсе перегружает маленький экран и заставляет выбирать между двумя
параллельными системами обозначений.

Presentation-слой должен получать уже выбранный active mapping:

```go
type ControlLabel struct {
      Label string
      Kind  ControlKind // keyboard или gamepad
}
```

Выбор active mapping не должен выполняться renderer-ом. Он должен опираться на
явное состояние input layer, например `HasController()`. Нельзя определять
наличие джойстика по тому, была ли недавно нажата его кнопка: подключенный, но
простаивающий контроллер все равно должен определять mapping.

Названия кнопок должны соответствовать физическим обозначениям устройства
настолько, насколько это позволяет SDL mapping. Для нестандартного контроллера
нужен нейтральный fallback: `Select`, `Back`, `Next`.

В Help можно показывать две отдельные секции, но они не должны одновременно
попадать в footer основного интерфейса:

```text
Gamepad
A Back   B Select   D-pad Navigate   L1/R1 Pages

Keyboard
Backspace Back   Enter Select   Arrows Navigate   P Pages
```

### 4.4. Визуальный формат

Подсказка состоит из короткого active control label и действия:

```text
[A] Back   [B] Open   [D-pad] Move   [L1/R1] Pages
```

При отсутствии джойстика тот же контекст отображается только с клавиатурой:

```text
[Backspace] Back   [Enter] Open   [Arrows] Move   [P] Pages
```

Требования:

- текст не должен перекрывать progress bar или playing status;
- длинные подсказки должны обрезаться предсказуемо;
- активный primary action должен отличаться от вторичных;
- цвет не должен быть единственным носителем смысла;
- при малой высоте окна подсказка может сворачиваться до 2–3 ключевых действий.

### 4.5. Ограничение 640x480

640x480 — обязательная базовая ширина для проектирования footer. Подсказки
должны помещаться в одну строку вместе с playing status и progress bar, без
уменьшения основного UI-шрифта.

Правила компактного layout:

- использовать короткие labels: `A`, `B`, `D-pad`, `L1/R1`, `Enter`, `Back`,
   `Arrows`;
- использовать короткие глаголы: `Open`, `Play`, `Back`, `Move`, `Focus`,
   `Edit`, `Apply`, `Cancel`, `Next`;
- не писать полные фразы вроде `Press Enter to confirm delete` в footer;
- разделять hints одним пробелом или малым фиксированным gap;
- сначала сокращать подписи, затем убирать второстепенные hints, и только
   потом переносить строку;
- не переносить один hint на две строки;
- primary action и cancel action должны оставаться видимыми всегда;
- при нехватке ширины скрывать вторичную навигацию, например `Pages`, но не
   `Open/Play` и не `Back`;
- для Delete confirmation оставлять только `Confirm` и `Cancel`;
- измерять итоговую строку в пикселях с текущим font face до рендеринга.

Примеры минимального набора для 640x480:

```text
Gamepad: [B] Open  [A] Back  [D-pad] Move
Keyboard: [Enter] Open  [Backspace] Back  [Arrows] Move
Edit: [Enter] Apply  [Backspace] Cancel  [Arrows] Change
Delete: [Enter] Confirm  [Backspace] Cancel
```

Точный состав hints определяется состоянием, поэтому это примеры допустимой
компактной формы, а не жестко зашитые строки.

## 5. Видимое состояние UI

### 5.1. Страница и источник

На верхней панели показывать страницу и источник отдельно:

```text
Library                                      Music
/music/ambient
```

Для remote-источников явно использовать названия `Modland` и `ModArchive`,
а не оставлять пользователю выводить источник из пути или формата строки.

### 5.2. Фокус панели

Текущая рамка панели должна иметь однозначный смысл. Нужно зафиксировать:

- inactive panel: обычный фон и обычный border;
- focused panel: усиленный border или контрастная полоса;
- selected row: highlight строки;
- focused action: highlight кнопки действия;
- editing value: отдельный highlight значения, не только панели.

Не использовать один и тот же визуальный сигнал для `selected`, `focused` и
`editing`.

### 5.3. Состояния, которые обязаны иметь текстовый маркер

Минимальный список:

- `Editing` — Settings изменяют значение;
- `Confirm delete` — удаление ожидает подтверждения;
- `Loading` — выполняется загрузка или обход каталога;
- `Partial` / `Unavailable` — список получен не полностью или недоступен;
- `Empty` — каталог корректно пуст;
- `No selection` — действие недоступно без выбранного объекта;
- `Playing` / `Paused` — состояние текущего воспроизведения.

Пустой список и ошибка чтения нельзя отображать одинаково.

## 6. Семантика Back

Back имеет иерархическое поведение, но его следующий результат должен быть
понятен из текущего UI.

Рекомендуемая семантика:

| Состояние | Результат Back | Подсказка |
|---|---|---|
| Settings editing | Отменить изменение | `Back Cancel` |
| Settings panel | Выйти из панели | `Back Exit settings` |
| Presets right panel | Перейти в левую панель | `Back Categories` |
| Library right panel | Перейти в левую панель | `Back Library` |
| Вложенный каталог | Подняться на уровень | `Back Up to ...` |
| Source root | Вернуться в `/` | `Back Sources` |
| Virtual root `/` | Закрыть UI | `Back Close` |
| Delete confirmation | Отменить удаление | `Back Cancel` |

Необходимо решить отдельно, должен ли Back из Settings/Presets возвращать в
последний Library-контекст или закрывать активную страницу. Решение должно быть
единым для всех страниц и покрыто тестами.

## 7. Help-страница

### 7.1. Место в навигации

Help — четвертая страница после Library, Settings и Presets. Цикл:

```text
Library -> Settings -> Presets -> Help -> Library
```

Обратный цикл:

```text
Library <- Settings <- Presets <- Help <- Library
```

Страница должна сохранять выбранную тему и позицию между открытиями. Переход
в Help не должен сбрасывать Library path, selected item или playback state.

### 7.2. Layout

Использовать layout, близкий к Settings:

- левая панель — список тем;
- темы и пункты, открывающие следующий уровень, имеют суффикс `/`, как
  директории в Library; конечные статьи отображаются без суффикса;
- правая панель — содержимое выбранной темы;
- активная тема имеет cursor highlight;
- содержимое не является интерактивным, если это явно не предусмотрено;
- длинный текст прокручивается по строкам или страницам;
- footer показывает действия Help.

В отличие от Settings, правая панель должна быть ориентирована на чтение:

- увеличить внутренние отступы;
- не использовать marquee для основного текста;
- сохранять стабильное начало строк при прокрутке;
- выделять заголовок темы отдельной строкой;
- показывать номер или индикатор страницы, если текст занимает несколько
  экранов.

### 7.3. Начальные темы

Темы следует разделить на операционные и справочные. Операционные идут
первыми:

1. `Getting started` — минимальный сценарий первого использования;
2. `Controls` — клавиатура и геймпад в зависимости от активного устройства;
3. `Library` — источники, панели, вход в каталог, Play;
4. `Delete` — область действия, подтверждение, ошибки и ограничения;
5. `Settings` — выбор и применение параметров;
6. `Presets` — выбор и применение визуальных пресетов;
7. `Formats` — поддерживаемые аудио и tracker-форматы;
8. `Catalogs` — Modland и ModArchive;
9. `Device` — PortMaster, desktop, разрешение и подключенный контроллер;
10. `About` — проект и автор.

`Getting started` должен быть коротким. Это не tutorial и не список всех
функций:

```text
1. Choose Music in Library.
2. Select a folder or file.
3. Press Enter to open or play.
4. Use Left/Right to move between panels.
5. Press Back to return or cancel.
```

Текст должен описывать фактический mapping после завершения этапа 2, а не
предполагаемый будущий mapping.

### 7.4. Тексты и форматирование

В первой версии текст хранить как Go-константы или статические структуры,
без markdown-парсера.

Рекомендуемая структура:

```go
type HelpTopic struct {
    ID    HelpTopicID
    Title string
    Lines []string
}
```

Требования к тексту:

- короткие строки, пригодные для ручного переноса;
- одна мысль на строку или небольшой блок;
- control labels выделены одинаковым способом;
- не использовать Unicode-символы, которых нет в Unifont;
- не полагаться только на цвет или жирность;
- не показывать технические внутренние имена вроде `focusPanel`;
- использовать пользовательские термины `Library`, `Music`, `Play`, `Back`.

### 7.5. Контекстный вход в Help

Help можно открыть двумя способами:

1. обычным переходом по циклу страниц;
2. отдельной командой `Help`, если для нее есть свободная кнопка или сочетание.

Если Help открыта отдельной командой, начальная тема должна зависеть от
контекста:

- Settings -> `Settings`;
- Presets -> `Presets`;
- Library -> `Library`;
- Delete confirmation -> `Delete`.

При переходе обычным циклом выбранная тема не должна неожиданно меняться.

### 7.6. Прокрутка содержимого

Не использовать marquee как единственный механизм чтения справки. Для правой
панели Help нужен вертикальный scroll offset:

```go
type HelpViewState struct {
    TopicCursor int
    ContentTop  int
}
```

Правила:

- Up/Down в левой панели меняют тему;
- Right переводит фокус в содержание;
- Up/Down в содержании прокручивают текст;
- Left возвращает фокус к темам;
- Back сначала возвращает фокус, затем покидает Help;
- при смене темы `ContentTop` сбрасывается в 0;
- заголовок темы остается видимым при прокрутке, если это помещается на экране.

## 8. Архитектура реализации

### 8.1. UIPage

Расширить `UIPage` значением `PageHelp`. Проверить все места, где используется
перечисление страниц:

- NextScreen и PrevScreen;
- page indicator;
- render dispatch;
- initial state;
- dirty flags;
- tests;
- app-level screen switching;
- shortcut handling.

Нельзя оставлять сравнения, предполагающие ровно три страницы.

### 8.2. Разделить модель и rendering

Добавить отдельные файлы по аналогии с существующей структурой:

- `internal/ui/help.go` — topic definitions and state;
- `internal/ui/render_help.go` — layout and drawing;
- `internal/ui/help_test.go` — state transitions and text layout;
- `internal/ui/action_hints.go` — context action model;
- `internal/ui/render_action_hints.go` — footer rendering, если helper станет
  достаточно крупным.

Help renderer должен использовать существующие primitives:

- list texture cache;
- panel background and border;
- cursor highlight;
- clipping;
- scrollbar;
- text rasterization.

Не создавать второй независимый механизм списка.

### 8.3. Action hints как pure mapping

Action hints желательно сделать чистой функцией или максимально изолированным
методом. На каждый набор входных состояний должен существовать ожидаемый набор
hints.

Проверять отдельно:

- Library local root;
- Library nested folder;
- Library right panel;
- remote catalog;
- Settings browse;
- Settings editing;
- Presets left/right panel;
- Help topic/content;
- Delete confirmation;
- loading/error/empty state.

### 8.4. Dirty state и resize

Добавление Help и footer не должно нарушить расчет panel height.

Проверить:

- высоту header;
- высоту breadcrumb;
- высоту playing status;
- progress bar;
- высоту footer hints;
- минимальное окно, где остается хотя бы одна строка списка;
- пересоздание текстур при смене разрешения, темы и transparency;
- отсутствие clipping нижней строки.

Footer должен иметь собственную вычисляемую высоту, а не занимать место
неявно поверх существующего playing status.

## 9. Доступность и читаемость

Для моноширинного fullscreen UI проверить:

- контраст текста, border и cursor highlight на светлой и темной теме;
- читаемость при минимальном разрешении PortMaster;
- отсутствие зависимости от цвета как единственного признака;
- достаточный размер активного элемента;
- стабильность layout при длинных названиях тем;
- корректное отображение кириллицы и поддерживаемых форматов;
- clipping без выхода текста за panel bounds;
- доступность всех действий с клавиатуры и геймпада;
- понятное состояние при отсутствии контроллера.

## 10. Тестовый план

### 10.1. Unit-тесты модели

Добавить тесты для:

- порядка страниц с `PageHelp`;
- сохранения Help topic cursor;
- переходов между topic panel и content panel;
- прокрутки и clamp `ContentTop`;
- сброса scroll при смене темы;
- выбора стартовой темы по контексту;
- генерации action hints для каждого состояния;
- fallback mapping без контроллера;
- корректного текста `Back` для каждого уровня навигации.

### 10.2. Property-like проверки

Проверить инварианты:

- cursor не выходит за границы списка;
- scroll offset не выходит за допустимый диапазон;
- переход по страницам всегда возвращается в Library после полного цикла;
- Help не изменяет playback state;
- открытие и закрытие Help не изменяет Library path;
- ни одна подсказка не содержит пустой label;
- строка подсказок не превышает доступную ширину после layout/truncation.

### 10.3. Интеграционные сценарии

Минимальные сценарии:

1. Новый пользователь открывает UI и видит доступные действия.
2. Пользователь входит в `music/`, открывает папку и запускает файл.
3. Пользователь переходит в правую панель и понимает, что там можно сделать.
4. Пользователь начинает редактировать Setting и видит `Apply/Cancel`.
5. Пользователь нажимает Back во время редактирования и не применяет изменение.
6. Пользователь начинает Delete и понимает объект подтверждения.
7. Пользователь открывает Help из Library и получает тему Library.
8. Пользователь открывает Help из Settings и получает тему Settings.
9. Пользователь возвращается из Help и сохраняет прежний Library context.
10. Пользователь отключает или подключает контроллер и получает корректные hints.

## 11. Acceptance criteria

Работа считается выполненной, если:

- на основном экране видны действия, доступные в текущем состоянии;
- пользователь может определить активную страницу, источник и панель без
  чтения исходного кода;
- Enter и Back имеют видимое объяснение для каждого основного состояния;
- Settings editing и Delete confirmation визуально отличаются от обычной
  навигации;
- Help содержит краткий Getting started и подробные операционные темы;
- Help использует фактический keyboard/gamepad mapping;
- основной footer показывает только active mapping: gamepad при подключенном
   джойстике или keyboard без джойстика;
- footer помещается на 640x480 без уменьшения основного UI-шрифта и без
   переноса одного hint на две строки;
- Help не сбрасывает Library path, selection или playback state;
- текст не обрезается критично на минимальном целевом разрешении;
- Help и action hints покрыты unit-тестами;
- `make test`, `make lint` и целевая сборка проходят при наличии системных
  зависимостей проекта;
- поведение проверено на клавиатуре и хотя бы одном типе контроллера.

## 13. Открытые решения

До реализации необходимо отдельно принять решения по следующим вопросам:

1. Показывать hints всегда или скрывать их после короткого периода бездействия?
2. Какой shortcut открывает Help напрямую, если такая кнопка потребуется?
3. Должен ли Back из Settings/Presets возвращать на Library или закрывать
   активную страницу?
4. Нужно ли сохранять последнюю страницу между запусками приложения или только
   в рамках одного запуска?
5. Должна ли Help содержать техническую информацию об авторе и лицензиях или
   только ссылку на внешнюю документацию?
6. Какой максимальный размер текста допустим для одной темы на минимальном
   разрешении?

Рекомендуемые default-решения для первой версии:

- hints показываются постоянно, но занимают одну компактную строку;
- при подключенном контроллере в основном UI показывается только gamepad
   mapping; без контроллера — только keyboard mapping;
- оба mapping доступны только в Help;
- 640x480 является обязательным размером для layout-проверки footer;
- Help открывается через обычный page cycle, без нового shortcut;
- Back сохраняет единый иерархический принцип и закрывает Help только после
  выхода из ее активной панели;
- состояние сохраняется в рамках текущего запуска;
- Help остается операционной, а лицензии и полная история проекта остаются
  во внешней документации.


## Реализовано: первый запуск и практическая справка

На первом отображённом экране отдельная плашка `[START] Open menu` (или `[TAB]`
для клавиатуры) показывается 10 секунд. Она не блокирует управление, не использует
уведомление трека и никогда не рисуется в feedback projectM. Таймер начинается
после загрузки, при первом рисовании. Открытие меню скрывает плашку и сохраняет
`ui.menu_opened=true`; истечение таймера не считается подтверждением, поэтому
при следующем запуске подсказка повторится. Старые настройки без поля получают
значение false. При смене подключения контроллера отображаемая кнопка меняется.

Help: Getting Started → Controls → Playback → Quality and Battery → Troubleshooting
→ Catalogs → Formats → Device → About → Licenses. Getting Started объясняет
первый сценарий без повторения подробного mapping из Controls. Положение темы относится
только к текущему сеансу; HelpTopicID соответствует индексу в embedded JSON.

Плейсхолдеры кнопок в Help разрешаются через тот же controlLabel, что и footer:
Nintendo A — открыть, B — назад, X — Play/Pause, Y — случайный пресет.
Клавиатурное переключение страниц обозначено P/N (назад/вперёд); вне меню эти
кнопки переключают пресеты. Обработка ввода не менялась.

Settings показывает пояснения выбранного значения под списком вариантов,
когда есть свободные строки. В режиме редактирования пояснение относится к
выбираемому значению. На маленьком экране полный текст доступен в Help.

Полные строки вида `**Section**` рисуются жирным, пустые строки разделяют
смысловые блоки, а очень длинные описания форматов автоматически делятся на
короткие абзацы.

Device info собирается только при первом открытии темы и кешируется. Источники
по приоритету: PortMaster environment, известные CFW/device-tree файлы, затем
существующие SDL/OpenGL/runtime probes. Catalogs показывает числа playable
tracks и folders непосредственно из metadata лениво открытых shuffle indexes.
